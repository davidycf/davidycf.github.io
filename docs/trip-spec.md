# 旅行网站产品行为

本文描述期望行为，不是当前行程清单；具体日期、默认卡、推荐数量和文本读 `data/`。代码若违反以下契约，应修代码；有意改变产品行为则同步修订对应契约与测试。

## 界面与日程
保留当前铁路线路/駅名標设计、城市色、中文与日文字体、站牌上下页导航、手机阅读布局。
六个主导航是“程 行程 / 宿 周边 / 食 吃 / 买 买 / 观 玩 / 要 附录”，不凭旧聊天恢复旧版五个图标，也不加第七个。
- 行程标题「行程 · 15 站」右边有“活动卡片 →”按钮进卡片库，卡片库标题右边有“← 行程”按钮回来（两页不再用并列的分段切换）；“和家里人共用 · 导出／导入”和“恢复推荐方案”放在行程列表最下面，读档提示和推荐方案更新提示仍在顶部。行程列表每天只写 DAY、站名、日期和标题，点进当天页；活动日的当天页显示“推荐方案／我的选择”、待选文字和提示，并有“换活动”（#dN-swap 直接展开）。卡片库 #cards 可搜中文、日文、内容与卡片 id（例如 ropeway），按已安排／未安排和亲子／街区／购物／地标／留白筛选；卡片页 #card-<id> 显示完整路线、支线、准备事项、资料，以及“安排到哪天”。
- 当天页顺序：站牌 → 标题区（标题、简介、ctx、judge、推荐方案／卡片详情／Museum 换日／换活动）→ 换活动面板 → 提示 → 支线摘要 → 票 → 今日路线 → 吃 · 买 · 看 → 住 · 今晚落点 → 这一天的准备 → 待确认 → 这一带还能… → 前后天。规划期和旅途中是同一个页面，不按日期切换模式。
  - 支线收成一行 `<details class="optsum">`：summary 写“支线 · 已选：…”（按选中顺序用顿号连接，含互斥组的当前项）或“支线 · 都没选（N 项可加）”，每次进入一天的页面（含 #dN-swap、换到别的日子）都是收起的；同一天原地重渲染（勾支线、撤销）时保持页面上的展开状态（模块变量 `optsOpen`，route(keep) 时读 details 的 open），焦点回到原勾选框。
  - 今日路线：活动日和卡片页的「推荐顺序」在时间段变化处插一行不计数的小标题（early/am 上午、noon 中午、pm 下午、eve 晚上），普通日没有。圆圈三种：固定事项实心加「固定」，卡片主线实心，只有勾了加项支线才出现的步骤（`opt` 指向不在互斥组里的支线）空心加「支线」；互斥组（例如 3/16 的上午）的步骤总会以其中一种出现，算主线、实心。
  - 吃 · 买 · 看 每行末尾有站链接，取自 view(d).rel（和「这一带还能」同一份，带 @支线 的照 refOn 规则）：食行 `吃 · <站> →` 和 `宿 · <酒店> 吃 →`（#base-T~eat），买行 `买 · <站> →`，观行 `玩 · <站> →`；某一行没有条目但有站链接时只放链接。
  - 住 · 今晚落点 最后一行是“回酒店 ↗”（info.json `hotels` 按 d.city 取，Google Maps 公共交通路线，新标签页），3/13 机上和最后一天不显示。
  - 这一天的准备只列没勾的，已勾的收进“已完成 N 项”（可展开取消勾选）；勾选时不重渲染，下次渲染再归类。卡片页和附录卡页仍全部列出。
  - 旅途中（todayN）当天页站牌的 DAY 后面有 TODAY。
- 一天一张主卡。换卡只改那一天；如果这张卡已经在别的日子，先确认“交换两天”或“移过来、原日改留白”；从卡片页替换已有主卡也要确认。都有一步撤销。日期的固定事项（樱家午饭、整理行李、酒店、移动日）永远不跟卡走。
- 三类提示：不可行（城市不符、移动日、每周固定休馆，按钮禁用并写原因）；待核对（日历未发布、已订票日期不符时提示实际票务要本人处理）；提示（重叠标签——也和带 covers 的固定日比较、路程远、回酒店晚、固定晚饭替换了卡片晚饭、某段当天休业、所选支线当天不可行时按默认显示）。不做暗中全局重排：重叠只提示，并给“取消这一项”按钮。
- 当天页的路线、标题、吃买看、这一带还能、准备清单、前后日名称，以及吃买玩站的“哪天会经过”，都由 app.js 的 `view(d)` 从当前卡和支线生成。改活动内容改 cards.json，改日期固定事项改 days.json 的 fixed，不要把活动写回日期。

## 方案、票务、冲突与导入
- 改支线、换卡后重渲染会把焦点放回同一个控件（按 data-act/card/opt 等稳定属性找），单选组可以连续用方向键切换。
- 用户要把自己的选择变成推荐方案时，改 days.json 的 slot.card 和卡片 opts 的 on，不需要改卡片正文。
- 各城市用同一套模型；每个城市有一张 multi 留白卡（rest-tokyo、rest-mishima、rest-osaka，箱根的 rest-hakone 随箱根卡保留），“移过来、原日改留白”用它。卡片库按 東京／三島／大阪／箱根 筛选；城市没有住的日子时（现在的箱根），卡片页写明只作资料保留。
- 跨多天的成组调整用 `presets`（options[].days 日期→卡，museum 指中签日，card 指登记票的卡），不要写成隐藏的全局重排。
- `plan.booked`{卡id: 日期id} 是本机登记的票；卡片也可以在 repo 里写 `booked`{day}。换掉登记日期上的卡时，卡片页“从这天移除”也走同一个确认流程，不直接改；换走以后那一天仍提示“登记在这天的票不在行程里”。`ticket:true` 的卡（teamLab、海游馆、横滨、四谷玩具馆、Museum）在当天页有「票」区块：订好后登记票面日期、改登记到这天、取消登记。`lottery:true` 的卡（Museum）没有登记时提示“模拟安排”。
- 任何会让已登记的票所属的卡离开票面日期的操作（换活动、卡片页安排或移除、交换、恢复推荐方案、导入）都先确认并写明“网页不会改票，实际票务要本人处理，登记会保留”；登记本身只能由用户手动更新或取消。
- 负担提示：一天里非默认的加项（不含爸爸单独）加上路程远、上午固定事项累计 3 项以上时提示；上午有固定事项（3/25 寄箱）又排了远程卡时提示会赶。
- 推荐方案更新提示：`jp27-base` 记着上次确认的推荐卡。repo 里的推荐改了以后，下次打开会列出哪几天变了，用户自选的天写明“保留你自己的选择”，点“知道了”后更新 base。
- 导出／导入（#plan，行程页“和家里人共用 · 导出／导入”）：导出 {format:"jp27-plan", v:1, exported, days 全部活动日→卡, opts 全部卡的支线 bool, booked, 可选 visited}，不含清单勾选、证件、订单号。导入先把文件补成完整结果再校验：缺的日期按推荐卡补上，缺的支线按卡片默认补上，互斥组按“文件明确选上的优先”归一。坏 JSON、格式、版本、未知或移动日、城市不符、休馆、同一张卡在完整结果里出现两次（含补上的推荐卡）都是错误，整份不导入；改名（aliases）、未知支线、互斥多选、缺的支线会回到默认、对不上的票或已逛过是提示，可以导入。预览列出每天的变化和每条支线的变化；按最终日期检查要保留的票（本机的，或勾了“也导入”就是文件里的），票面日期不再是那张卡时写明。票和已逛过和本机不同时要单独勾选才覆盖，否则保留本机。只有“检查”过的那份文字能导入：检查后再改输入框，预览和两个勾选都作废。一次应用、可撤销。用户把导出的文字交给 Claude 时，照 days 改 data/days.json 的 slot.card、照 opts 改卡片支线的 on，就成了新的推荐方案。
网页 #museum「Museum 换日」：选抽签结果 → 预览四天的变化（含自选会被换掉的天、当天提示）→ 一次应用，可撤销；只改这四天，3/25 寄箱等固定事项不动。预览里“你自己选的”按逐日来源 plan.via 判断：方案页排的天记 via，之后换活动、交换、卡片页安排或移除、恢复推荐、导入都会清掉那天（或全部）的 via，所以只有方案刚排、没再动过的天不算自选。“我已经中签”的勾选只对当前选中的日期有效，换预览日期就清掉，已有登记被改日期时会写明。中签前一律显示为模拟安排；用户勾“我已经中签”才在本机 plan.booked 登记，登记不会因换卡、恢复推荐或应用别的方案被删，Museum 移离登记日期时提示实际票务要本人处理。总览大阪段显示当前是哪种安排及登记状态。
- Museum 仅改 preset 中的日期；海游馆及日期固定事项不随换日移动。矩阵从 `cards.json` 读取。

## 待办
没勾的有 due 待办分三种：过期（今天 > due）、接下来（from ≤ 今天 ≤ due）、以后；已勾的不算。附录「尚待确认」排序：过期和接下来按 due 升序，然后以后按 due 升序，然后没有 due 的照数据顺序；已勾的收进最后的“已完成 N 项”（勾选时不重排，下次渲染再归类）。有 due 的待办在文字后面带日期标记（接下来 `2/18` 或 `12 月` 粗体，过期 `已过期 · 10/15` 用 --check，以后 `2/18` 浅色；同一年写 M/D，跨年写 2027/2/18），当天准备和附录卡相关待办也带标记但不重排。附录导航的“待办 N”在有过期或接下来时后面加小圆点。行程首页倒计时下面的“接下来”最多两条（过期在前，再按 due），超过两条时第二行加“等 N 项”，每条是日期标记加文字的第一个分句（到第一个“：”“（”“；”“，”为止，最多 24 字），数据里可写 `short` 覆盖；整行链到 #info-todo；没有时整块隐藏；卡片待办只在 todoActive 时算。待办可带 `ref` 指向详情所在：`info-<附录卡 id>`、`info-<A–E>` 或 `base-<酒店>`／`base-<条目>`（例如 3/14 改到达时间 `base-T`），勾选框旁显示「详情」链接（在 label 外面，点它不会勾选）；属于日期的待办都要有 ref。
- 日期、卡片、附录共用稳定勾选键；取消或换卡不清空历史勾选。due/from 格式见 [data-model.md](data-model.md)。

## 宿与吃买玩
- 宿：按近场/步行圈/更远分三圈；可筛吃饭、嘗 好好吃一顿、甜点、购物、看逛、孩子放电、九点以后。O32 道頓堀今井 本店从 O11 道顿堀名物里拆出来单独一条，O11 只写大阪烧、章鱼烧、串炸。有搜索：宿首页两家一起搜，单个酒店页的搜索与用途筛选叠加。每个地点有稳定 id（如 T21），#base-T21 直达并高亮；新增地点给新 id，不复用旧 id。宿的地点按用途也出现在吃买玩里，数据仍只有 base.json 一份：「吃」取 `k` 含 eat 或 snack，「买」取 shop，「玩」取 see 或 kids；night 不作为投影条件（eat+night 的大統領仍进「吃」，只有 night 的不进）。东京、大阪每条线路第一站是酒店站卡（双线边框和「宿」字章，数量从数据算），三岛没有。从吃买玩进宿的网址是 #base-T~eat、#base-T10~eat 这类：页面写明只看哪些用途、可以“看全部用途”回 #base-T；返回链接回「吃 · 全部站」等来源，底栏高亮来源；前后酒店链接保留来源；用途胶囊只列这一范围里有的，筛选按 酒店+来源 分开记，不串到普通宿页。未知后缀回到不带后缀的地址，不存在的条目回到酒店页，范围外的条目改成普通宿链接。吃买玩的搜索直接包含这一范围的宿条目（写明「宿 · 酒店」和圈层，链接带来源，标题链接把搜索词带进宿）；搜到酒店的站名、假名、罗马字或酒店名时，带出这家酒店这一范围的全部条目，和搜站名带出整站一样。引用条目自己的 tag、所在站或宿那条命中时，结果里出宿那一条（只出一次），并写“也在「吃 · 日本橋」：tag”，链接回那一站。宿页和吃买玩的合并搜索用同一个 baseMatch()（条目文字、酒店站名／中文写法 zh（心斋桥）／假名／罗马字／酒店名、引用条目的 tag 和所在站），从搜索结果点「宿 · 酒店 →」带着搜索词进宿，看到的条目和结果里一样；带来源的宿页也算上那本书引用的宿条目（inBook）。同一家店只存一份：books 条目写 {base:"O18", tag} 就是引用宿的那条，站页照常列出、内容从宿读，搜索只返回宿那条。
- 吃／买／玩按城市列站牌索引、独立站页和全文搜索。酒店周边用宿投影，不重复存数据；新站 code 不与宿 ID 冲突。吃买玩的站页顺序：站名 → head/lead → 今天这样挑 → 路线 hint → 条目 → 兜底 → 哪天会经过 → 上下站。吃的「索引」A1 先讲通则再讲料理：日本吃饭的节奏 → 连锁兜底（按场景选连锁店，不按品牌保证门店设施）→ 便利店 → 寿喜烧／烧肉 → 天ぷら… → 大阪烧…。「吃」首页在城市线路之前有「好好吃一顿」总览：从 books 和 base 里所有 treat 条目派生（不另存副本），按城市分组，默认收起（summary 写“嘗 好好吃一顿 N 家 展开”，这次打开页面期间记住展开状态，不存本机），每项写店名、所在站或「宿 · 酒店」、吃什么的第一句和价格（晚餐超预算的写午餐区间并标推荐午餐，其余写最低到最高），链接到 #eat-<站>-<id> 或 #base-<id>~eat。
- 没有住宿日的城市（由 days.json 推出，不加字段）：吃买玩首页不在原位置列出，放到最底部（索引与心得之后）收起的「备用 · 箱根 1 站」里，这次打开页面期间记住展开状态，有搜索词时照常出现在结果里；卡片库没选城市筛选、也没有搜索词时（包括「未安排」筛选）收成「箱根 3 张 · 现在没有住箱根的日子」，选了「箱根」或搜索时直接展开。
- 夜间内容并入“宿”；旧 #eat-N1、#see-N1 跳转 #base。旧站和附录深链通过 MOVED 跳转表保持兼容。#d1–#d15 永远指同一天，不随卡片移动。

## 附录
- #info 是附录索引：顶部吸顶的分节导航（待办、A–E、怎么用，标签取标题“｜”前的短名，横向滑动，随阅读位置高亮：每次滚动都重新算，取标题已越过吸顶条下方阅读线的最后一节，滚到页底取最后一节，往回滚也会跟着变），然后「尚待确认」待办，再按节列卡片（名字、“：”后的要点、待办数、清单已勾数）。#info-<id> 是单张卡的页面：面包屑回到所在节、全文、清单、官方链接、详情指向这里的待办（同一份勾选）、“哪天会用到”（当前方案里哪几天的页面或当前卡片资料链到这里，或当天准备里的待办 ref 到这里）、前后卡（跨节连续）。从卡片页返回索引时停在那张卡上。#info-A–E、#info-todo、#info-ref 仍滚到索引对应位置；未知 id 回到 #info。
- 附录按 A–E 分节，卡片独立深链；引用使用 `附录#id`。改名或移节不破坏链接；清单、待办及「哪天会用到」随当前方案派生。
- 保持已有 favicon、Apple touch icon、manifest 和铁路站牌视觉；保留移动端和无障碍布局。
