# 数据模型与内容录入

先读目标 JSON 的现有条目及 `app.js` 相关读取逻辑。以下是约定及兼容契约；当前具体数据以 JSON 为准。新增字段时同时修改生产者、消费者与相关验证，不另存派生数据。

## 文件与日期模型
- data/days.json：15 天。普通日是旧的整日结构（ja/ro/area/title/sub/plan/stay/eat/shop/see/note/rel/judge）。活动日多一个 `slot`，去掉了 ja/title/plan 等活动内容，只留：`id`（"0315" 这类稳定日期 id）、`slot`{card 推荐卡, suggest 换活动时首屏推荐, pending 未选时显示的待选文字, half 只允许半天卡时写原因（3/19）}、`ctx`（当天作息语境，例如倒时差补觉）、`fixed`{plan/eat 里带 `at` 的固定事项, short 列表页显示的固定事项短语}、`stay`、`note`、`rel`。固定晚饭条目标 `dinner:true` 和 `label`（例如 3/18 酒店附近早吃收行李）；固定午饭同理标 `lunch:true` 和 `label`（3/19 樱家）。普通日也可以带 `covers`（例如 3/23 海游馆 `aquarium`），让东京卡和固定日一起做重叠提示。
- data/cards.json：`tags`（重叠标签：label，`visit:true` 的可以标“已逛过”）、`aliases`（卡片改名或合并时旧 id → 新 id）、`cards`（活动卡片）。
- data/books.json（吃买玩站）、data/base.json（宿）、data/info.json（todo、aliases 附录卡改名映射、apx 附录、ref、hotels 回酒店导航：{city, name, q}，name 是官网正式名称，q 是官网公开的日文地址（不带邮编，Google Maps 按地址定位最准），不写订单信息；三岛和羽田不在「宿」里，所以不放 base.json）。

## 活动卡片
- `id` 永久稳定，不用下标、标题或日期；删除或合并时在 `aliases` 里留映射。`city`、`size`（half/full）、`name`（列表里的名字）、`ja`/`ro`（站牌大字与罗马字：只写地名——车站或街区，不写景点名，景点名留给旁边的 name／title，日文景点名（例如 東京タワー）要留在 name/title/summary 等会被搜索的字段里，卡片库才能用日文搜到；跨两地可写「上野・秋葉原」，留白卡例外）、`area`、`title`、`summary`。
- 事实：`time`、`transit`（写“估计”，不要伪造精确分钟）、`load`（near/mid/far）、`family`、`booking`、`rain`、`hours`、`closed`{dow: number[], text: string}（每周固定休馆＝硬性不可安排）、`calendar`（日历未发布等待核对文字，只提示不阻止）、`late`（回酒店晚，和当天晚上的固定事项冲突时提示）、`avoid`{dow: number[], text: string}（能去但不该去的星期，例如 Skywalk 周末，只提示不禁止）、`multi`（可以放在多天，例如留白卡）、`checked`（核对日期）。
- `opts` 支线：{id, label, on 默认是否勾, group 同组互斥单选, who:"dad" 爸爸单独, covers 重叠标签, closed 按星期不可行（同下方结构）}。`route`/`eat`/`shop`/`see` 的每条是 {text, at(am/noon/pm/eve，仅 route), opt 选了才显示, unless 没选才显示, who, dinner, lunch, withFixedDinner, closed, alt}：`dinner:true` 是卡片的晚饭建议，当天日期有固定晚饭时不显示并给出说明；`lunch:true` 同理对应固定午饭；`withFixedDinner:true` 只在当天有固定晚饭时显示（例如“直接回去赶上晚上的安排”）；`closed`{dow: number[], text: string} 加可选 `alt` 表示这一段在某个星期不可行（例如 2k540 周三休业），那天显示 alt 或跳过并提示，不禁止整张卡。
- 卡片、支线与路线等条目的 `closed`，以及卡片的 `avoid`，均使用 `{dow: number[], text: string}`：`dow` 必须是整数数组（0=周日…6=周六），即使只有一天也写成数组，例如 `{dow: [2], text: "周二休馆"}`，不能写 `dow: 2`。
- `covers` 卡片级重叠标签；`rel` 是 "eat:T5" 这类资料引用，"shop:T8@ginza" 表示选了该支线才算经过；`todos` 是 info.todo 的 id，"water-bus@pm-boat" 同理；`checks` 是附录 checklist 的 id；`links` 官方链接。
- route 和 fixed.plan 的文字不以 `上午：`、`中午：`、`下午：`、`午后：`、`晚上：` 开头（时间段由 `at` 显示成小标题），具体时刻（`10:00 前后：`）可以写。需要备用方案或细节的步骤用 `\n` 分段：第一段写要做的事，后面的段落显示成小字；日期页的 plan 字符串同样可以分段。
- 卡片文字不能假定日期：星期、休馆按实际日期算；“哪天晚饭”“今天是第一天”这类写在日期的 ctx/fixed 里。
- 反过来，活动日的 `stay`、`note` 只写酒店、夜晚和日期本身的事实，不写当天活动（例如不能写“奈良当天往返”“海游馆结束就回”），因为卡片随时会换；ctx 只写星期、假日、作息这类日期语境。

## 餐饮字段、价格与链接
- 吃饭条目（books.json 的 eat 条目、base.json 带 eat 的条目）可选字段：`treat:true`（嘗 好好吃一顿）、`budget`（食べログ予算，每个大人一餐：[lo, hi] 是不分午晚的一个区间，{lunch:[lo, hi], dinner:[lo, hi]} 分午晚，只有一餐就只写那一餐；lo 为 0 表示「～¥999」，hi 为 null 表示「¥30,000～」；照食べログ的档位原样抄（用店页顶部的午／晚「予算」，顶部有几餐就写几餐；顶部是「-」的那一餐可以用「口コミ集計」的数字；两者午晚方向相反时先不写，等用户定，例如中清用户选了口コミ集計），显示成“食べログ 午 ¥1,000–1,999 · 晚 ¥3,000–3,999”；晚餐下限 ≥ 10,000 而午餐不到时自动显示“推荐午餐 · 晚餐通常超预算”。非 嘗 的吃饭条目也可以写）、`sig`（吃什么：招牌菜和它好吃在哪）、`order`（怎么点，可省）、`arrive`（几点到：一句话写几点到最好和原因，例如“午饭建议 11:20 左右到、11:30 开门；平日 14:00–17:00 中休”；显示在 嘗／食べログ 那一行之后、吃什么之前，总览不显示）。嘗 条目必须有 `arrive`，非 嘗 可选；推荐午餐的店（overDinner）只写午饭；提前到店和订位时间是按营业时间推导的建议，不承诺免排队或有空席，不写没核实的排队时长，不绑定日期、不改活动卡或固定事项；营业时间、中休、能否预约由用户交 GPT 研究、PR 审查核对，新增 嘗 店资料没齐时在 PR 里列出缺哪几家。这几个字段进搜索（价格区间、“食べログ”、推荐午餐提示和“几点到”都能搜到，吃和宿共用 mealText()）；`treat` 不是 `k` 用途。嘗 条目的 tag、body、fam、note 不写具体金额，价格只放在 budget，分量和点法照写（例如“一条”“一条半”）。宿首页酒店卡的用途计数不放 嘗：嘗 出现的地方旁边都有文字“好好吃一顿”。吃买玩首页的站点行：标题（area）旁边有 嘗 印（只在「吃」、站里有 嘗 条目时，不写数字），右侧只写经过的 DAY 和箭头（没有日子时只有箭头），项数和兜底数只在站页的駅名標下面写。「吃」的两张酒店卡在“酒店步行圈”后面写 嘗 印和家数，右侧仍是“N 处 →”和住宿日期；买、玩不写 嘗。books.json 的条目可带 `id`（小写字母、数字、连字符，在同一本书里唯一，不用下标），#eat-<站>-<id> 直达并高亮；嘗 条目必须有 id；站 code 写错时跳到条目实际所在的站。books.json eat 条目可带 `fb:true`（兜底：商场餐饮层、店铺目录、回酒店吃这类现场五分钟就能找到的）：站页在普通条目之后的「兜底」小标题下每条一行（店名＋tag＋地图按钮），整行是 `<details>`，点开是原来的 body、fam、links；编号和“N 项”只数普通条目，有兜底时写“+M 兜底”；搜索结果同样一行，命中只在正文里时自动展开；#eat-<站>-<id> 进来自动展开并高亮。每站至少留一条普通条目；整站都是补给性质的（例如天保山）不标兜底。条目 body 可以用换行分段（每行一段），配 **加粗** 写小标题。
- 放题使用普通条目，不增加 嘗、专用标签、筛选或总览；正文保留「放题／食べ放題／自助」供搜索。budget 使用全店食べログ区间；套餐价显著高于该区间时注明。儿童免费年龄按来源写，核对日期准确保留。

## 待办和引用
- 待办可带 `card`（和可选 `opt`）：只在那张卡（那条支线）排进行程时出现在附录待办里；没排的收在卡片页，勾选状态一直保留。附录 checklist 条目同样可带 `card`。属于日期本身的待办（Skyliner、三岛酒店、樱家营业日、新干线开售、寄箱、羽田酒店等）写在 days.json 那一天的 `todos` 里；每天的「这一天的准备」先列日期的待办，再列当前卡的待办，和附录是同一份勾选。不属于某一天的（eVISA、Museum 抽签、出发前弄清退税流程、JR 改点）只在附录。少数有明确时间的待办带 `due`（"2027-02-18" 那天要做或最晚这天前做完；"2027-02-18 19:00" 带钟点，例如芝加哥晚上 7 点开售的车票，标记写出钟点，当天都算接下来、第二天才算过期；"2026-12" 只知道月份，按月底算，确切截止钟点写在文字里，例如 Museum 抽签截止芝加哥 12/31 8:59）和可选 `from`（从哪天起算“接下来”，省略时取 due 前 30 天，月份写法取那个月 1 日前 30 天）；日期按设备本地日期比较（规划时是芝加哥，到日本后是日本），不用 jstToday()。
- `ref` 指向 `info-<附录卡 id>`、`info-<A–E>` 或 `base-<酒店/条目>`；日期待办必须有 ref。待办显示行为见 [trip-spec.md](trip-spec.md)。
- 文字里引用附录：`附录#<id>` 由 fmt() 转成「附录 B · 三岛两晚」这样的链接（节字母和短名从数据读，卡换节自动跟着变）；日期、卡片、吃买玩里引用附录都用这种写法，指到具体那张卡。整节的“附录 A–E”仍转成节链接，只在确实指整节时用。「Museum 换日」也自动转成链接。
- 附录每张卡有全局唯一、稳定的小写字母/数字/连字符 `id`，不得使用 todo、ref 或单字母；`short` 可选，链接放在对应卡。移节不改 ID，改名用 `aliases`，保持既有深链。
- `base.json` 同一店只存一份；`books.json` 可用 `{base:"O18", tag}` 引用。宿、书、附录及待办新增条目用稳定 ID，不复用或依赖数组下标；旧 ID 兼容见 app.js 的 aliases / MOVED。
- 酒店导航 `q` 使用官网公开日文地址，不写邮编及订单信息。
