# 存储、共享与离线契约

涉及 `app.js` 的 store/commit/sanitize、`cloud.js`、`sw.js`、`firestore.rules` 时读本文件及相关实现。当前版本号、缓存名、SDK 版本从代码读取，不在文档重复维护。

## 本地方案
- 本设备选择存在 localStorage `jp27-plan`：{v:1, days{日期id: 卡id}, opts{卡id: {支线id: bool}}, visited{标签: 日期id}, booked{卡id: 日期id}, via{日期id: 方案id}}；上次看到的推荐方案在 `jp27-base`（旧版 `jp27-plan.base` 首次迁移至此）。app.js 里页面读 `plan`，所有改动经 commit() 算出改了哪几条记录（change：days{日期: {card, via}}、opts 只放普通支线、groups{卡: {组: 支线}}、booked、visited，null 表示删掉回到推荐／默认）交给 store；撤销一次还原整次改动的全部记录，并核对这些记录还是这次写下的值、恢复的卡没有排在别的日子。互斥组读入时只留一个（卡片顺序里第一个选上的）。勾选 `jp27-todo` 取消时删掉这个键。支线跟着卡走，切回原卡会恢复。读不出来、版本不支持、卡已删除、卡排不进那天（城市不符、休馆、3/19 只排半天，和 app.js 的 blockOf() 同一套规则）、已逛过记录指向不存在的日期时按推荐方案显示并说明；万一渲染出错，页面给出“清掉本机活动选择并重新载入”的按钮；存储不可用时照常显示，提示不能保存。“恢复推荐方案”只清 days/opts/via，保留已逛过、登记的票和勾选。登录家里名单上的账号后方案和勾选在两台手机间同步（见「和家里人共用」）；没登录时只在本机，换设备用导出／导入。
- 没登录时浏览器 localStorage 保存勾选，阅读偏好一直只在本机；不承诺和旧 Sites 状态同步。普通待办是 {id, text}，勾选按 todo:<id> 保存，插入、排序、改文案都不串项；新增待办给新 id，不复用旧 id。旧版按下标保存的勾选不会按位置套用，页面提示重新核对，用户点“知道了”后才清掉旧键；附录 checklist 的状态不受影响。

## 共享与事务
与家庭菜单共用 Firebase 项目、成员名单及 SDK；同一浏览器共用登录。

- 数据：Firestore `trip/plan` = {v:1, days{日期: {card, via}}, opts{卡: {支线: bool}}（只放普通支线）, groups{卡: {组: 支线}}, booked{卡: 日期}, visited{标签: 日期}}；`trip/ticks` = {v:1, items{勾选键: true}}。只存 ID 和状态，不存姓名、邮箱、修改人、订单号、价格。写入按 FieldPath 字段级：日期记录整条替换，删除用 deleteField()，文档由创建事务建好，日常只 update。
- 写入方式（commit 的 kind）：单项（支线、已逛过、勾选、单日换成没安排的卡，换入换出都不是可登记票的卡）直接写，最后写入为准，断网进 Firestore 队列，服务端确认后才有撤销；交换、移动、带票务确认的换卡、票面登记和撤销在线时事务里核对所见的记录再写，断网时对照本机看到的再排队；换卡核对的记录包括换入、换出两张卡的登记的票（预览后才登记的也拦下，重新确认时带票务提醒）和这张卡已经排在的其他日期（预览时就在的可以留着，之后新增或变动的拦下），撤销核对同样这些记录；Museum 换日、导入、恢复推荐、迁移只在线做（断网提示联网），导入、恢复推荐、迁移还要求登记的票和预览时一样。核对不过时页面更新并提示“刚改过，请再确认一次”。
- 读入：sanitize() 把共用数据校验成页面看的样子，坏值、不认识的卡按推荐显示并说明，不回写；碰到这个版本看不懂的记录（未知卡、支线、换日方案、类型不对）时改那一条会被拒、提示刷新，其他照常能改；恢复推荐和导入遇到就整次停下。v 不是 1 时整份只读。
- 同一张卡被两台手机同时排进两天：每一天都提示并链到其他日期，再安排这张卡时列出全部现有日期。
- 首次：登录不会上传。家里还没有共用行程时 #plan 显示本机摘要和“用这台设备的方案创建共用行程”（事务里缺哪份建哪份）。已有共用行程、这台设备（按账号）第一次接入且有差异时，显示家里的方案并提供“用家里的”或“查看并迁移本机选择”（复用导入预览，按当时勾的选项写明哪张登记的票会离开票面日期，勾或取消“也用这台设备登记的票”时马上重算；票、已逛过、额外勾选默认不选）；处理后在本机 `jp27-cloud-joined` 记下。退出登录回到本机原来的 jp27-plan、jp27-todo，两边互不影响。
- 本机还有：`jp27-cloud-cache`（共用方案的快速副本，带 uid；下次打开在连上之前只读显示；退出、不在名单、被拒时删除）、`jp27-base`（每台设备自己确认的推荐基线）。旧下标勾选只留本机。
- 状态标记（行程首页倒计时后面，链到 #plan）：家里共用／待同步／只能看／保存失败／本机方案（登录了但还没用共用方案）。离线横条在共用方案来自本机副本时加“家里方案上次同步 M/D HH:mm”。
- 别人改了方案：页面原地更新（保留路由、滚动、焦点、支线展开），toast 写“共用行程已更新：3/16 换成…”；自己写入的回执不提示；已经打开的确认、Museum“我已经中签”、导入预览、迁移勾选都作废重来。
- 规则在 firestore.rules 的 trip 段：只开放 trip/plan、trip/ticks 的读、创建、更新（不能删），查顶层字段白名单、v == 1、各 map 大小；动态嵌套键由网页校验。改了要贴到控制台发布。规则可用模拟器或现有 fakefb 测试；发布后用未登录请求确认读不到。
- 断网：这台设备确认过的账号（本机有它的共用副本）、浏览器确实存下了 Firestore 离线数据时（第一次快照来了、没有退回内存缓存；Firestore 退回内存时只在控制台打一条 “Falling back to memory cache” 警告，cloud.js 看这条；还没确认时 #plan 写明改动要在这个页面等到同步完），断网打开仍按成员身份用 Firestore 的本机副本，换卡、交换、移动、支线、票面登记、勾选、撤销都排队，联网后同步，并马上再问一次名单（不在了就停下、删副本、回到本机方案）。#plan 写明断网时能不能改、还缺什么。首次登录、创建、迁移、Museum 换日、导入、恢复推荐要联网。

## Service worker 与版本一致性
- 离线：sw.js 在根目录，当前 `jp27-core-*` 缓存 存页面本身（导航和 index.html 都用 `./` 这个键，忽略 query 和 hash）、app.js、cloud.js、五个 data/*.json、manifest 和四个图标。这些文件网络优先、4 秒超时，失败、超时或非 2xx 时从保存的副本返回并加 `x-jp27-from-cache: 1`；副本里也没有时照常报网络错误。页面、app.js 和五个 JSON 是同一次发布的一组：网络取到的新文件先放进这个标签页自己的暂存缓存（`jp27-next-<client id>`，加 `x-jp27-saved` 保存时间头），页面用五个全新的 JSON 正常启动、cloud.js 也取到且接口版本（CLOUD_API；connect() 接口变化时两边一起升级）一致后发 `jp27-commit`，SW 等这个标签页的暂存写完、确认整组（页面、app.js、cloud.js、五个 JSON）都在，才把这一组写进副本；启动出错或只取到一部分时副本不动。manifest 和图标随取随存，install 和每次页面在线打开后补上缺的。发布的那一组只整组进副本：还有完整的旧副本时只等标签页的 `jp27-commit`；什么副本都没有时（第一次打开）install 和在线打开时一起取整组，全部取到、app.js 和 cloud.js 的 `CLOUD_API = N` 一致才存（所以两边保持这一行的写法）。每次整组写进一个新的缓存（`<缓存名>@<时间>`，带清单、manifest 和图标），全部写进去才替换这个缓存名下其他的副本；写到一半失败（例如空间不够）就删掉新缓存，原来那组照常用。断网时这一组都从同一份有完整一组的副本返回（先看当前缓存名的，再看旧的；每份按它自己的清单算完整），不按文件拼。每个响应带 `x-jp27-copy` 写明来自哪份；一次启动的五个 JSON 来自不同副本时（另一个标签页刚好存了新的一组），页面改从同一份副本整组重读。缓存名只在 sw.js 的缓存逻辑或清单改动时才换，发布新内容不用改 sw.js。换了缓存名后，旧的 `jp27-core-*` 留着照常离线用，等新的存齐了（发布的一组经过一次正常启动）才删。缓存里另存一份清单 `jp27-core.json`，页面用它判断是否存齐。Google Fonts 存在 `jp27-fonts`（缓存优先，CSS 后台更新，最多 300 条），不算“可离线”的条件。Firebase SDK（`www.gstatic.com/firebasejs/<版本>/`）存在 `jp27-sdk`：缓存优先，页面连上后（第一次打开时等 SW 接管之后）让 SW 预取 cloud.js 用的三个模块和它们 import 的文件，SW 存完回话，页面再查一次断网能不能改；副本里 cloud.js 的 `V = 'x.y.z'` 不再用的版本在下一次保存副本时删掉（所以 cloud.js 里保持这一行的写法）。登录页和 Firestore 请求照常走网络。其他同源文件和所有外部链接（地图、官网）都不缓存。
  页面按 data 响应头判断（不用 navigator.onLine）：全部来自缓存时 `<main>` 前的离线横条写“离线版本 · 保存于 M/D HH:mm”（五个 JSON 里最早的保存时间，设备本地时间）。混合时（有的新、有的来自副本，可能是两次发布，例如新 days.json 引用了旧 cards.json 里没有的卡）改用副本里的整组五个 JSON，横条写“网络不稳，这次显示的是…保存的版本”；副本不全时才照混合显示，写“部分资料来自…”。行程首页状态行倒计时后面有小标记：清单存齐是“可离线”，SW 已注册但没存齐是“正在保存离线版本”，不支持 SW 或 CacheStorage 时不显示。读不到数据时提示“这台设备还没保存离线版本：连上网络打开一次就会保存”。本机选择和勾选的 localStorage 和离线无关，照常保存。
