# 家里的饭：项目专属规则

本目录为独立的家庭菜单工具，不加载日本行程的文档。遵守仓库根 `AGENTS.md` 的全局协作、隐私和发布规则；修改共享的 Firebase 规则时同时检查两个应用。用途：从自家菜谱随机排饭并生成购物清单。

- 文件：index.html（骨架和全部 CSS）、app.js（界面和抽菜）、store.js（数据和保存）、defaults.js（初始菜谱，用料按 4 人份）。无构建步骤，ES module。
- 样子是小饭馆的墙：白瓷砖、横杆上挂一周的菜牌、绿墙裙上放「抽一周」按钮。菜牌颜色有含义：荤菜红、素菜绿、主食黄（`其他` 类是灰的）；辣菜有「辣」字印，定下来的菜有红图钉。菜名用 Ma Shan Zheng 毛笔字，其余用 Noto Sans SC。底部三栏：菜（这周吃）、买（买菜）、谱（菜谱）。
- 数据：localStorage `family-menu-v2` = {settings, plan{slots{'日期|午饭/晚饭': {id, locked}}, extras}, recipes{items}, have{items}}。界面只通过 `store.apply(change)` 改数据（store.js 顶部写了 change 的格式），换成和家人共用时只换 store 的实现。旧版的 `family-menu-v1` 第一次打开时整份接过来（自加的菜、菜单、勾选、设置），旧键保留不删。
- 规则：再抽一次只换没定的菜；改天数、顿数、开始日期时按“第几天的哪一顿”保留已排的菜，空出来的用「补上空着的 N 顿」补；改人数只重算清单。买菜清单按人数换算，个/根/只这类向上取整，克数取整到 5 或 50；调料（group 调味品）只列名字。抽菜、删菜、改菜、恢复菜谱都能一步撤销。「这周顺便做」的早饭和甜点在「这周吃」里可以自己挑、换或者这周不做（整周重抽时随机挑；设置里关了“顺便排”只留已经挑了的）。
- 旧版的 `#share=` 分享链接：先问再换上这周的菜单，自己的菜谱只加不减。新版用「复制这周的菜」「复制清单」和打印。
- 和家里人共用（cloud.js）：Firebase 项目 `cyu-ghpages`（免费的 Spark 方案，不升级），Google 登录 + Firestore，SDK 从 gstatic 按版本号加载（以代码为准），不加载 Analytics。网页配置是公开的，写在 cloud.js 里。数据在 Firestore `menu/settings`、`menu/plan`、`menu/recipes`、`menu/have` 四份文档，字段和本机版一样；每次改动只写碰到的字段（set merge），两个人同时改不同的菜、勾不同的东西不会互相盖掉。
- 谁能用：`members/{uid}` 里有文档的 Google 账号。名单只在 Firebase 控制台里加，仓库里不写邮箱；登录了但不在名单里的人在设置里看到自己的编号（uid）发给管理的人。访问规则在仓库根目录 `firestore.rules`，改了要贴到控制台 Firestore → 规则 并发布才生效。
- 第一个连上的家里人把自己设备上的整份数据放上去；之后每台设备第一次连上，只把自己加的、共用菜谱里没有的菜加进去，其余以共用的为准。共用时这台设备留一份副本（`family-menu-cloud-cache`），下次打开先显示它、连上之前只能看不能改；退出登录或不在名单里时删掉副本，回到本机自己的那份。Firestore 自带离线副本，没网时改动先显示、连上网自动存，设置按钮上的小圆点：灰＝只在本机，绿＝共用中，黄＝有改动没存上或现在只能看。
- 测试：本地存在时运行 `.dev/menu.mjs`（不提交），覆盖抽菜、定菜、设置变化、清单换算、菜谱增改删、旧版迁移、坏数据、旧分享链接、320–1280px 无溢出和打印。`.dev/sync.mjs` 用 `.dev/fakefb.mjs` 假的 Firebase SDK（同一套名单规则、推送给所有页面）测两台手机：首次上传、不在名单、第二个人合并、实时同步、同时改、离线、撤销、副本只读、退出登录、登录出错。本地可用模拟器或现有 fakefb 测试规则；规则发布后用不登录的 REST 请求确认读不到。
